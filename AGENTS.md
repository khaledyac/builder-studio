# AGENTS.md · Builder Studio platform

You are helping build **Builder Studio**, an internal vibe coding platform. Business users ("AI builders") describe an app in plain language. Agents build it in an isolated workspace, one per session, while the builder watches a live preview. Publish opens a pull request, and GitHub deploys the app to its domain's GCP spoke according to its risk tier.

- **Architecture:** `docs/architecture.md`. Read the sections your step links to before writing code.
- **Plan:** `docs/plan/README.md`. You work on one step at a time: `docs/plan/steps/NN-*.md`.

## Hard rules

- **Generally available Google Cloud services only.** No preview or beta features, no `gcloud beta` or `gcloud alpha`. Use the `hashicorp/google` Terraform provider. Use `google-beta` only for a GA feature that is missing from `google`, with a comment saying why.
- **No secrets** in code, config, tests or logs. Secrets live in Secret Manager. CI authenticates with Workload Identity Federation, never with keys.
- **Every model call goes through `libs/trustlayer`.** Never call Vertex AI or any model API directly. Always pass the user, app and session IDs.
- **Agent-written code runs only inside a session workspace.** Hub services never execute generated code.
- **Contracts in `contracts/` are the source of truth.** They are Pydantic models. JSON Schema, OpenAPI and TypeScript types are generated from them. Change them only in a step that says so, and bump their version.
- **Production has no human write access.** Pipelines deploy everything.

## Stack

- Python 3.14 (the standard build, not free-threaded) with uv (one uv workspace), FastAPI, Pydantic v2 and pydantic-settings, pytest, ruff, pyright.
- Task (`Taskfile.yml`) runs every command, locally and in CI. There is no Makefile.
- Web UI (`web/`): React, TypeScript, Vite, Vitest, Playwright.
- Builders' apps (project types): generated by Copier from the platform templates, with the same Python 3.14, Pydantic and Task conventions. Pages are server-rendered with FastAPI, Jinja2 and HTMX unless a step says otherwise.
- Infrastructure: Terraform. CI/CD: GitHub Actions. Commits follow Conventional Commits.

.claude/skills/ the skills code assistants use: shipped with the plan, then kept current by builder-kit's agents layer (never edit them here)

Everything the app repos use lives in a second repository, `builder-kit`, created in step 10: the Copier layers (`templates/agents`, `templates/base`, `templates/types/<type>`, `templates/packs/<domain>`), the skills, the shared GitHub workflows and the approved app Terraform modules. The platform generates the builders' app repos, one per app. `docs/plan/README.md` describes all three.

## Code rules

- KISS first, then DRY, then SOLID kept light. No abstract class until a second implementation exists. The exceptions are the interfaces named in `contracts/` and the adapters a step asks for.
- Type hints everywhere. Keep functions short: under 40 statements, complexity under 10.
- Pydantic models for every data shape that crosses a boundary: API bodies, contracts, settings, Firestore documents, events, task payloads, tool inputs and outputs, and structured model outputs. No raw dicts across boundaries. Validate a model's output with Pydantic before acting on it.
- Every service has a health endpoint, emits structured JSON logs carrying `user_id`, `app_id` and `session_id` when known, and sends OpenTelemetry traces.
- Anything triggered by Cloud Tasks, Pub/Sub or a webhook must be idempotent.
- Tests:
  - unit tests for logic,
  - integration tests against the local stack (`task dev`),
  - contract tests for every API in `contracts/`.

## Commands

- `task dev` starts the local stack. `task dev-down` stops it.
- `task test`, `task lint`, `task fmt`.
- `task contracts-check` regenerates the schemas and types from the Pydantic models and fails on any drift.
- `task tf-validate` runs fmt, validate and the security scan on Terraform.
- `task --list` shows every task.

## How to work on a step

1. Read the step file and the architecture sections it links.
2. Write a short plan: the files you will touch and the tests you will add. For a size L step, split it into tickets with `to-tickets` first, then build them with `implement-spec`. If the step is unclear or contradicts the architecture, ask before coding.
3. Work test-first and stay inside the step's scope. Note anything out of scope as a follow-up.
4. Run `task lint test`, plus `task tf-validate` for infrastructure, until everything is green.
5. Update the docs your change affects. Record any real decision as an ADR in `docs/adr/`.
6. Open a pull request titled `NN · <step title>`, with its description written by `pr`, that lists the acceptance criteria and how each one is met.

## Definition of done

- Every acceptance criterion in the step is met and shown in the pull request.
- Lint, types and tests pass locally and in CI.
- No secrets, no direct model calls, no non-GA service.
- Contracts, docs and ADRs are updated where needed.
